# Four-Person Work Split & Exam-Safe Plan

## User context / constraints

- Four members.
- Strong web-development/dashboard skills.
- No hardware confirmed; budget currently ₹0. Some electronics may be borrowed later.
- Main agent GPT 6 Astra Max in OmniRush.
- The user says an end-term exam is tomorrow. Exam preparation takes priority.

## First session (tonight / pre-exam): bounded, low-attention

1. Extract the starter pack and open it in OmniRush.
2. Paste the one-shot prompt.
3. Have the agent spend the initial bounded phase on file reading, competitor research, architecture and a project TODO. Do not wait by the computer.
4. Allow only small, reversible repo/file changes. No paid services, global installs, cloud database, OAuth, or high-risk configuration.
5. Save a clear checkpoint before studying/sleeping.

Do not promise a finished product overnight. Use the exam day only for a very short status check if necessary; resume implementation after the exam and rest.

## After the exam: build blocks

### Block 1 — Scope freeze (30–45 min)

- Read the market-gap verdict.
- Freeze one scenario and one differentiator.
- If direct competition already performs the whole event-linked workflow, choose a narrower, evidence-backed wedge or clearly position this as an educational prototype rather than a novel market claim.

### Block 2 — Core functionality first (2–3 hours)

Build the typed event data, deterministic scenarios, reconciliation function and test coverage before spending time on visual polish.

### Block 3 — Web deck + demo integration (2–3 hours)

Complete five presentation slides, transitions, speaker notes and embedded demo scenario.

### Block 4 — Research/economics/architecture (1–2 hours)

Confirm sources; distinguish actual costs from assumptions/quotes required; explain connectivity, calibration, security, maintenance and data reliability.

### Block 5 — Test and rehearse (2 hours)

Run all deterministic scenarios, open the app in a browser, inspect console errors and screenshots, rehearse the 10-minute story, and prepare a video/screenshot fallback.

## Ownership (four people)

- **Member 1 — Frontend:** presentation controls, visual system, charts/cards and accessibility.
- **Member 2 — Simulation/data:** scenario generator, event model, reconciliation rules and tests.
- **Member 3 — Research/product:** competitor comparison, official sources, user problem, risks and economics.
- **Member 4 — Integration/pitch:** story, speaker notes, merge/integration, judge Q&A, backup demo and final delivery.

Everyone reviews the final pitch. Each artifact has exactly one owner.

## Definition of the first useful demo

The presentation opens; Slide 4 can start a normal delivery scenario, then a discrepancy scenario; the application computes and explains the numerical difference; a missing-data case is shown; all examples say `SIMULATED`; reset works; and the team can explain which sensors would be needed in a field pilot.
